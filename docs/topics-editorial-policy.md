# トピックコーナー 編集方針（初版 2026-10-14）

「トピック」（/topics/）は、障害のある方とご家族の暮らしにかかわる法律・制度の改正を、少していねいに解説する常設コーナーです。
この文書は、記事を書く側（人・AI を問わない）と、記事を点検する側が共有する基準です。
**文体ルール（全記事共通）** と **構成プロファイル（記事の類型ごと）** に分かれています。
この初版は Claude が起こしたもので、河原さんの手直しを経て確定します。

- 機械で確かめられる項目は `scripts/topic-lint.mjs` が検査する（違反は件数で出る）
- 書き手とは別の編集者役が `scripts/topic-review-prompt.md` の観点で採点する
- 法的な正確さ・言い回しの品位・取り上げる価値の判断は、河原さんの検品に残す

---

## 1. 読者と立ち位置

- 読者は二層。**福祉の現場の支援者**（グループホーム・就労支援の職員、相談支援専門員）と、**障害のある方のご家族**。
  専門職向けの深さを持ちながら、家族が読んで「自分たちに何が起きるか」が分かる書き方にする。
- 書き手は「制度を解説する人」であって「制度を宣伝する人」でも「不安をあおる人」でもない。
  良い点と、まだ決まっていない点・注意すべき点を同じ温度で書く。
- 読者がこの記事だけで個別の判断をすることは想定しない。最後は必ず原典と相談先に戻す。

## 2. 文体ルール（全記事共通）

### 2.1 文のつくり

- **一文一義。** ひとつの文でひとつのことを言う。接続助詞（〜が、〜ので、〜ており）で3つ以上の節をつなげない。
- 目安は1文 **100字以内**。条文を引く文や列挙を含む文は例外だが、120字を超えたら分ける。
- 段落は2〜5文。1文だけの段落を2つ以上続けない（箇条書きで書いたものを段落に戻しただけの文章になる）。
- 語尾を単調にしない。「〜です。〜です。〜です。」と同じ語尾が4文続いたら、体言止め・疑問・引用・「〜でした」などに言い換える。
- **断定と留保を使い分ける。** 条文に書いてあることは言い切る（「〜になります」「〜は削除されました」）。
  条文の意図や今後の運用の読みは留保をつける（「〜と読めます」「〜と読むべきでしょう」「〜が視野に入っている書きぶりです」）。
  両者を混ぜない。

### 2.2 言葉の選び方

- 専門用語は初出で短い添え書きをする。例：「判断能力（事理弁識能力）」「職権で（本人や親族の申立てがなくても裁判所の側から）」。
- 条文の言葉と、日常の言葉を**並べて**出す。例：「『重い・長い・降りられない』制度から、『必要な分だけ・必要な間だけ』の制度へ」。
- 具体例は「」で短く挙げる。例：「預貯金の払戻し」「施設の利用契約の締結」「遺産分割協議」。
  抽象的な「さまざまな場面」「適切な対応」で済ませない。
- 数字には**時点と出典**をつける（「令和7年12月末時点、最高裁『成年後見関係事件の概況』」）。
- 条文を引くときの省略は「…」で示し、記事末尾で「読みやすさのため一部を省略しています」と断る。
- 「障害」の表記は法令名・制度名は原文どおり、それ以外は本サイトの用法（「障害のある方」）に合わせる。

### 2.3 使わない表現（AI 文体の癖として機械検査の対象）

次の表現は使わない。lint が検出する。見つけたら言い換えるのではなく、**その文が何を言いたかったのかを考え直して**書き直す。

| 使わない | 理由 | 代わりに |
|---|---|---|
| いかがでしたか／いかがでしょうか | 読者への呼びかけが空疎 | 書かない |
| まとめ（見出し）／まとめると | 要約の見出しは不要。結論は本文の中で言う | 最終章は「〜が考えておくこと」 |
| 〜と言えるでしょう／〜と言えます | 断定を避ける癖。根拠があるなら言い切る、なければ「〜と読めます」 | 言い切るか、根拠を示して留保 |
| 〜していきましょう／〜しましょう | 読者を動員する語り | 「〜が要ります」「〜しておくと〜」 |
| 重要です／大切です／ポイントです／注目されています／求められます／期待されます | 何がどう重要かを言っていない | 具体的に何が起きるかを書く |
| 〜することが可能です | 「〜できます」で足りる | 〜できます |
| 〜について解説します／〜について見ていきましょう／本記事では | 前置き | 導入は「何が変わるか」から始める |
| さまざまな／多様な／適切な／しっかり／きちんと | 中身のない修飾 | 具体例に置き換える |
| 〜など（1段落に3回以上） | 列挙を途中で投げる | 挙げきるか、代表例1つにする |
| 一方で（1記事に4回以上）／また、（文頭、1記事に8回以上） | 接続の癖 | 文の順序で関係を示す |
| 〜とは（見出し）／〜について（見出し）／〜のポイント（見出し） | 見出しが中身を言っていない | 見出しは言い切る（例：「3つの類型が1つになる」） |
| 〜ではないでしょうか／〜かもしれません（1記事に4回以上） | 留保の連発 | 留保は本当に不確かな所にだけ |
| ！ | 本コーナーでは使わない | 。 |

### 2.4 構造の作法

- 見出しは「番号. 短い名詞句 ― 言い切りの一文」の型を基本にする。例：「1. 全体像 ― 3つの類型が1つになる」。
- 太字は**結論の一文、または対比の片側**にだけ使う。1記事で 25 箇所を超えたら多すぎる。
  Markdown の `**` は、直前が日本語文字だと太字にならない。`**` の直前は句読点・空白・改行にする。
- 箇条書きは、並列で順序のない項目にだけ使う。本文の説明を箇条書きに逃がさない（本文の行数に対する箇条書き行の割合が 25% を超えたら多い）。
- 比較は表（Markdown テーブル）か新旧対照（`.taisho`）で見せる。文章で「現行は〜、改正後は〜、現行は〜」と往復しない。
- 囲みの使い分け：
  - `.topic-lawref` 法令名・番号・成立/公布日（冒頭）
  - `.topic-schedule` 施行日・締切（dl）
  - `.topic-toc` 目次（見出しのアンカーと一致させる）
  - `.taisho` 条文の新旧対照（`.taisho-head` / `.taisho-body` / `.new` / `.old` / `.jo` / `.kesu`）
  - `.point` 読みどころ（「読みどころは4つです」＋①②③④）
  - `.chui` 誤解しやすい点・注意
  - `.topic-figure` 図版（alt は図の内容を文章で説明する）
- 末尾は固定の型：関連する nest のページへの導線 → `---` → 出典（一次情報、URL つき） → 省略・免責の但し書き。

### 2.5 事実の扱い

- 法令名・法令番号・条番号・日付・金額・人数は、**一次情報で確認できたものだけ**書く。確認できなかった点は本文に「（未確認）」と明記して残す。推測で埋めない。
- 出典は go.jp／courts.go.jp／lg.jp などの一次情報。報道・解説サイト・まとめ記事を出典にしない（調査の手がかりに使うのはよい）。
- 「まだ決まっていない」ことは、決まっていないと書く（施行日の政令、省令の内容、運用通知）。
- 個人名・個別事例の個人情報は書かない。

## 3. 構成プロファイル（記事の類型）

記事を書く前に、取り上げる情報がどの類型かを決める。類型は PR 本文と `タスク.md` に明記する。
判定が割れるとき（例：改正法の施行に伴う運用通知）は、**読者にとって主役は何か**で決め、迷った理由を PR に書く。
lint は `--type` でプロファイルを切り替える。

| 類型 | 情報源の例 | 読者が知りたいこと | 必須の要素 | 推奨の要素 | 文字数の目安 |
|---|---|---|---|---|---|
| **1 法改正解説型** | 成立・公布された法律、改正法 | 何がどう変わるか、いつから、自分はどうなるか | lawref、schedule、目次、新旧対照（1か所以上）、「いま利用している人はどうなるか」、「〜が考えておくこと」 | point、chui、図版 | 4,000〜8,000 |
| **2 通知・運用変更型** | 厚労省通知・事務連絡・Q&A、こども家庭庁通知 | 現場の手順の何が変わり、何が変わらないか | 発出日・発出元・宛先・文書番号、「変わること／変わらないこと」の対比、現場の手順への落とし込み、「〜が考えておくこと」 | 通知本文の引用（`.taisho` の片側か引用枠）、chui | 2,000〜4,000 |
| **3 報酬・基準改定型** | 報酬改定、基準省令・告示、解釈通知 | 対象サービス、数値、経過措置、期限 | 対象サービスの明示、変更点の表（旧→新）、経過措置と期限、事業所の対応、「〜が考えておくこと」 | 単位数の計算例、chui | 2,500〜5,000 |
| **4 パブコメ・審議中型** | e-Gov 意見募集、審議会・部会の資料、法案 | 何が論点か、いつまでに何ができるか | 「決まったことではない」の明示（冒頭と末尾）、論点の整理、締切と意見の出し方（URL）、今後の見通し | 賛否それぞれの立場の要約 | 2,000〜4,000 |
| **5 制度紹介・活用型** | 信託・税制・年金・扶養共済など既存制度 | 使える人、手続き、費用、落とし穴 | 使える人の条件、手続きの流れ、費用・税の扱い、よくある誤解（chui）、相談先 | 比較表（似た制度との違い）、具体的な場面の例 | 2,500〜5,000 |
| **6 統計・動向型** | 後見関係事件の概況、利用状況調査、白書 | 数字が何を示し、何を示さないか | 数字の出典と時点、前年との比較、「数字から言えること／言えないこと」、読者への含意 | 図版（グラフ）、表 | 1,500〜3,000 |

全類型に共通して必須：frontmatter（title／date／summary／`draft: true`）、導入段落で「何が変わるか（何の話か）」を一言で、末尾の出典（一次情報 URL つき）、免責の但し書き。

### 類型ごとの注意

- **1 法改正解説型**：新旧対照は、変わった箇所を `<b>` で示す。条番号が同じで中身が入れ替わった条文は、その旨を `.kesu` で補足する。経過措置（附則）を必ず扱う。
- **2 通知・運用変更型**：通知は法律ではない。「義務」「努力義務」「技術的助言」の別を書く。自治体で運用が異なりうる点は、そう書く。
- **3 報酬・基準改定型**：単位数・加算の名称は告示どおりに書く。「増える／減る」だけでなく、どの事業所にどう効くかを書く。経過措置の終期を schedule に入れる。
- **4 パブコメ・審議中型**：案の段階であることを読者が見落とさないよう、冒頭の `.chui` と末尾の両方で言う。意見提出の URL と締切は schedule に入れる。
- **5 制度紹介・活用型**：改正ニュースではないので「変わる」という書き出しにしない。対象者の条件を最初に出し、当てはまらない読者が早く分かるようにする。費用・税は金額の根拠（条文・通達）を示す。
- **6 統計・動向型**：数字を並べるだけにしない。1つの図か表に絞り、「この数字から言えないこと」を必ず1段落書く。

## 4. 点検の分担

| 項目 | 誰が | 手段 |
|---|---|---|
| 禁止表現・語尾・文長・箇条書き率・太字・必須要素・出典 URL・文字数・build | 機械 | `node scripts/topic-lint.mjs <記事> --type <1-6>` |
| 読みやすさ・論理の運び・読者への配慮・類型の必須要素が中身として満たされているか | 編集者役（書き手と別の AI） | `scripts/topic-review-prompt.md` の観点で採点 |
| 法的な正確さ、条文の読み、言い回しの品位、取り上げる価値、公開の可否 | 河原さん | PR のレビュー。`draft: true` を外すのは河原さんだけ |

lint と編集者役を通っても、それは「書いたことが基準に当たっている」という意味でしかない。公開の判断は河原さんが行う。

## 5. この文書の育て方

- 河原さんが記事を直したら、直した理由のうち一般化できるものをこの文書に足す（2.3 の表、3 の必須要素）。
- 類型 2〜6 は、最初の1本を河原さんが直したものが、その類型の見本になる。見本ができたら `docs/topics-examples.md` に記事パスと「何が良いか」を書き足す。
- lint の閾値（文長・太字数・箇条書き率）は、公開済み記事が通ることを基準に調整する。公開済み記事が通らない基準は基準の側が間違っている。
