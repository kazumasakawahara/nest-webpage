1. 3つの場所と、つなぐ2つの動き

ファイルの置き場所は3つあります。つながっているのは GitHub を経由する経路だけ で、Mac とクラウドが直接やり取りすることはありません。

Mac（手元）~/projects/nest-webpage
あなたが編集する場所。Claude デスクトップアプリのセッションもここを触る。
push →⇄← pull
GitHub（中継点）kazumasakawahara/nest-webpage
ここに載って初めて「確定」。main へのマージで本番サイトが更新される。
pull →⇄← push
クラウド（Claude）使い捨てのコンテナ。セッション開始時に GitHub から複製し、終了後しばらくで消える。
いちばん大事なこと。 どちらの場所でも、commit と push をしていない変更は、その場所にしか存在しません。 クラウドはコンテナごと消え、Mac も作業ディレクトリの整理で消えます。「GitHub に載ったか」が、安全かどうかの境目です。

main と作業ブランチ

main は本番サイトの元になる本線です。作業は別名のブランチ（例 topics-quality-gate）で行い、GitHub の PR（プルリクエスト） でレビューと CI を通してから main に合流（マージ）します。マージ済みのブランチは消してかまいません。

3. 毎回の型（これだけ守る）

作業前 main を最新にしてから、作業ブランチを切る

git switch main
git pull --ff-only origin main
git switch -c 作業名   # 例: git switch -c news-2026-10-20

作業後 必ず commit と push まで。ここで終わらせない

git add -A
git commit -m "何をしたか（日本語でよい）"
git push -u origin 作業名

push すると GitHub が「Create a pull request for … by visiting:」と URL を出します。その URL を開くか、Claude に「PR を作ってマージまで」と頼めば、main への合流に進めます。

マージ後 main に戻って最新を取り込み、終わったブランチを消す

git switch main
git pull --ff-only origin main
git branch -d 作業名
この3ブロックで日常の9割は済みます。--ff-only は「素直に進められる時だけ進む」という安全弁で、分岐していれば止まって教えてくれます。

4. こう出たら、こうする

止まった Need to specify how to reconcile divergent branches.

「分岐しているので、合わせ方を指定して」という意味。壊れてはいません。まず、自分がどのブランチに居るかを見ます。 作業ブランチに居たまま git pull origin main をすると、こうなります。

# main を最新にしたいだけなら、main に移ってから
git switch main
git pull --ff-only origin main

一度だけ次を実行しておくと、以後は安全な進め方だけで pull するようになります。

git config --global pull.ff only

止まった Your local changes … would be overwritten by checkout.

未コミットの変更があって、切り替え先のブランチと同じファイルが違うため、切り替えられません。変更を退避してから切り替えます。

git stash push -u -m "退避の名前"
git switch main
git pull --ff-only origin main

退避したものの扱いは、次の項目へ。

確認 退避（stash）した中身を、戻すか、捨てるか

git stash list                        # 退避の一覧
git stash show --stat --include-untracked   # 新規ファイルも含めた一覧
git stash show -p                     # 変更の中身
中身がやること
GitHub（main）にまだ無い作業元のブランチに戻り git stash pop で復元 → commit → push
すでに main に入っている作業の重複git stash drop で捨てる（取り消せないので、中身を見てから）
判断がつかないそのまま残しておき、Claude に git stash show -p の出力を貼って判定を頼む
今回の実例。 退避した中身は「ブランチ上で未コミットのまま1日置かれていた6ファイル」で、GitHub のどこにも無い作業でした。復元してブランチ名を付け直し、push して PR #103 でマージしました。

止まった Not possible to fast-forward, aborting.

--ff-only の安全弁が働いた状態。作業ブランチに居るのに main を取り込もうとした時に出ます。main に移ってから pull するか、作業ブランチに main を入れたいなら git merge main を使います。

衝突 CONFLICT (content): Merge conflict in …

同じファイルの同じ場所を両側で変えた時に出ます。タスク.md と 作業ログ.md は両側で末尾に追記するので、衝突しやすいファイルです。自分で直すなら、ファイル内の <<<<<<< から >>>>>>> までを読んで両方を残すか片方を選び、印を消して git add と git commit。迷ったら、その状態のまま Claude に「衝突を解消して」と頼めば、クラウド側で引き受けられます。

正常 Fast-forward / Already up to date / Deleted branch …

すべて正常です。Fast-forward は素直に進んだ印、Deleted branch はマージ済みブランチを安全に消せた印です。

正常 no changes added to commit

git stash pop の直後などに出ます。変更は作業ディレクトリに戻っていて、まだ git add していないだけ。続けて git add -A すればよい状態です。

5. コマンド辞典（今回使ったもの）

コマンド何をするか
git statusいまの状態（ブランチ、未コミット、GitHub との差）を表示。迷ったらまずこれ。
git switch 名前ブランチを切り替える。-c を付けると新しく作って切り替える。
git fetch originGitHub の最新状態を「知るだけ」。手元のファイルは変えない。
git pull --ff-only origin mainGitHub の main を手元に取り込む。素直に進めない時は止まる。
git add -Aすべての変更（新規ファイル含む）を、次の commit に入れる準備をする。
git commit -m "…"準備した変更をひとまとまりとして記録する。
git push -u origin 名前ブランチを GitHub に送る。-u は次回から git push だけで済むようにする印。
git branch -m 新しい名前いま居るブランチの名前を変える。
git branch -d 名前マージ済みのブランチを消す。未マージなら拒否される（安全）。
git stash push -u -m "…"未コミットの変更を、新規ファイルごと名前を付けて退避する。
git stash list / show / pop / drop退避の一覧 / 中身 / 戻す / 捨てる。
git log --oneline -5直近5件の commit を1行ずつ見る。
git merge main作業ブランチに main の変更を入れる（作業ブランチ上で実行）。

6. Claude に頼む時の言い方

クラウドで作ったものは、Claude が commit と push をしない限り消えます。依頼の終わりに次の一文を付けると、取りこぼしが無くなります。

「終わったらブランチにコミットして push まで。PR の作成とマージは私が指示する」

Mac 上のセッション（デスクトップアプリ）でも同じです。セッションを閉じる前に「commit と push まで済ませて、ブランチ名を教えて」と言う習慣にすると、今回のような「1日置かれた未コミット」が起きません。

場面ごとの頼み方

場面言い方
main に入れたい「このブランチの PR を作ってマージまで進めて」
記録だけの小さな変更「main へ直接 push して」（毎回その都度）
衝突が出た「衝突を解消して」＋画面のスクショ
退避したものの判定「git stash show -p の結果です。戻すべきか判定して」
Mac に取り込む手順が知りたい「手元に取り込むコマンドを教えて」

7. やらないこと

コマンド理由
git push --forceGitHub の履歴を書き換える。他の場所（クラウドや別の Mac）の状態と食い違い、復旧が難しくなる。
git reset --hard未コミットの変更を即座に消す。取り消せない。
git checkout -- ファイル / git restore ファイルそのファイルの未コミットの変更を消す。意図して使う時以外は避ける。
git stash drop（中身を見ずに）退避したものを捨てる。見てからでないと、今回のように未送信の作業を失う。
main 上で直接編集して pushPR と CI を通さず本番に出る。記録ファイルの追記のように影響が無いものだけ、その都度判断する。
エラーが出た時に、エラー文の中の「hint:」をそのまま実行しないこと。hint は一般論で、いまの状況に合っているとは限りません。まず 4 章を見て、無ければスクショを Claude に。
